# [설계 결정] 배포 구조

- 날짜: 2026-11-16
- 관련 이슈: #1 (실제 구성은 프로토타입 배포 단계에서 한다)

앱 EC2와 DB EC2를 분리하고, 무중단 배포는 Nginx 블루그린으로, 데이터는 DB EC2를 중지·시작하는 방식으로 보존한다. 비용 수치는 모두 미측정이며, 리전과 사양을 정한 뒤 계산한다.

## 공통 제약

- 측정할 때만 띄운다 (하루 2시간 이하).
- 월 예산은 5만원 이하다.
- 부하 생성기(k6)는 대상 서버와 다른 장비에서 실행한다.

## 설계 결정 1. DB 배치

- **상황:** 부하 테스트로 앱과 DB의 성능을 측정해야 한다. 예산이 작다.
- **선택지:**
  - A. 앱과 MySQL을 EC2 한 대에서 Docker Compose로 운영
  - B. 앱 EC2와 DB EC2를 분리 (Docker MySQL)
  - C. 앱 EC2 + RDS
- **결정:** B
- **이유:**
  - 앱과 DB가 자원을 나눠 쓰지 않아 측정값이 분리된다.
  - MySQL 설정, 백업, 장애를 직접 다뤄 볼 수 있다.
  - RDS보다 비용이 적을 것으로 예상한다 (미측정).
- **감수한 점:**
  - 백업, 패치, 장애 복구를 직접 운영해야 한다.
  - 관리형 DB의 실무 경험은 얻지 못한다.

## 설계 결정 2. 무중단 배포 방식

- **상황:** 단순 재시작으로 배포하면 그동안 서비스가 중단된다.
- **선택지:**
  - A. EC2 한 대 + Nginx 블루그린 (앱 컨테이너 2개)
  - B. ALB + 인스턴스 2대 롤링 배포
  - C. ECS나 CodeDeploy 같은 관리형
- **결정:** A (프로토타입은 단순 재시작으로 배포하고, 블루그린은 개선 단계에서 적용한다)
- **이유:**
  - 추가 비용이 거의 없다.
  - 전환 원리와 graceful shutdown(SIGTERM)을 직접 구현하고 검증할 수 있다.
- **감수한 점:**
  - 인스턴스 자체가 죽는 장애에는 대응하지 못한다 (단일 장애점).
  - 실무형 ALB 구성은 경험하지 못한다.
- **검증 계획:**
  1. 단순 재시작 배포를 하는 동안 k6를 돌려 중단 시간과 실패 요청 수를 측정한다.
  2. 블루그린을 적용하고 다시 측정한다.
  3. 결과는 [성능 개선] 또는 [장애 대응] 기록으로 남긴다.

## 설계 결정 3. 환경 생성·삭제와 데이터 보존

- **상황:**
  - 측정할 때만 띄운다.
  - 대량 데이터로 "데이터가 많을 때의 동작"을 시험해야 한다.
  - 매번 데이터를 재생성하거나 import하면 측정 시간(2시간)을 잡아먹는다.
- **선택지:**
  - A. 매번 시드 스크립트로 재생성
  - B. EBS 스냅샷에서 복원
  - C. S3 덤프에서 import
  - D. DB EC2는 삭제하지 않고 중지·시작만 해서 EBS 볼륨을 유지
- **결정:** D. 시드 스크립트는 저장소에 두어 언제든 재생성할 수 있게 한다.
- **이유:**
  - 복원 시간이 없다.
  - 스냅샷 복원 볼륨의 첫 읽기 지연(지연 로딩)이 없어 측정이 왜곡되지 않는다.
  - 프라이빗 IP가 유지되어 앱 설정이 바뀌지 않는다.
- **감수한 점:**
  - 중지 중에도 EBS 저장 비용이 계속 나간다 (미측정).
  - 측정을 반복하면 데이터 상태가 바뀌므로, 필요하면 시드 스크립트로 초기화해야 한다.
- **IaC 구성:**
  - 앱 쪽(EC2, Nginx)은 Terraform `apply`/`destroy`로 매번 생성하고 삭제한다.
  - DB 쪽은 별도 state(또는 `prevent_destroy`)로 분리해 실수로 삭제되지 않게 한다.
  - AWS 예산 알림을 설정한다.
- **S3:** 사용하지 않는다.
  - Terraform state는 로컬에 둔다.
  - 이미지는 컨테이너 레지스트리(GHCR)로 옮긴다.
