# [설계 결정] 배포 구조

- 날짜: 2026-11-16
- 관련 이슈: #1 (실제 구성은 프로토타입 배포 단계에서 한다)

앱 EC2와 DB EC2를 분리한다. 무중단 배포 방식과 데이터 보존 방식은 보류하고 나중에 정한다. 비용 수치는 모두 미측정이며, 리전과 사양을 정한 뒤 계산한다.

## 공통 제약

- 측정할 때만 띄운다 (하루 2시간 이하).
- 월 예산은 5만원 이하다.
- 부하 생성기(k6)는 대상 서버와 다른 장비에서 실행한다.
- 환경은 Terraform `apply`/`destroy`로 생성하고 삭제한다. AWS 예산 알림을 설정한다.

## 설계 결정 1. DB 배치

- **상황:** 부하 테스트로 앱과 DB의 성능을 측정해야 한다. 예산이 작다.
- **선택지:**
  - A. 앱과 MySQL을 EC2 한 대에서 Docker Compose로 운영
  - B. 앱 EC2와 DB EC2를 분리 (Docker MySQL)
  - C. 앱 EC2 + RDS
- **결정:** B
- **이유:**
  - 앱과 DB가 자원을 나눠 쓰지 않아 측정값이 분리된다.
  - MySQL 설정, 백업, 장애를 직접 다뤄 볼 수 있다.
  - RDS보다 비용이 적을 것으로 예상한다 (미측정).
- **감수한 점:**
  - 백업, 패치, 장애 복구를 직접 운영해야 한다.
  - 관리형 DB의 실무 경험은 얻지 못한다.

## 보류 1. 무중단 배포 방식

- **보류 이유:** 프로토타입은 단순 재시작으로 배포한다(문제를 일부러 해결하지 않는 단계). 무중단 배포는 개선 단계에서 필요하다.
- **정할 시점:** 개선·재측정 단계 전. 그 전에 단순 재시작 배포의 중단 시간과 실패 요청 수를 k6로 측정해 둔다.
- **고려사항:**
  - 환경을 측정할 때만 띄우므로 ALB처럼 시간당 과금되는 구성도 비용이 크지 않을 수 있다 (미측정).
  - 배포 중 중단 시간과 실패 요청 수를 측정할 수 있어야 한다.
  - 실무에서 흔한 구성(ALB + 롤링, 관리형)과 원리를 직접 다루는 구성(Nginx 블루그린)의 학습 가치 차이
  - 단일 인스턴스 구성은 인스턴스 장애에 대응하지 못한다.

## 보류 2. 데이터 보존과 DB 환경의 생성·삭제

- **보류 이유:** 데이터 규모가 정해지지 않았다. 규모에 따라 재생성·복원 시간이 달라진다.
- **정할 시점:** 요구사항 정의에서 데이터 규모를 정한 뒤, 기준 측정 단계 전.
- **고려사항:**
  - 측정 재현성: 개선 전후를 비교하려면 매번 같은 초기 데이터에서 측정해야 한다.
  - 준비 시간: 하루 2시간 안에 복원·재생성까지 끝나야 한다.
  - 중지 중 고정비 (EBS, 고정 IP, 미측정)
  - DB를 실수로 삭제할 위험 (Terraform state 분리, `prevent_destroy` 등)
  - 콜드 스타트: MySQL 메모리 캐시가 빈 상태로 시작하므로 측정 전 예열 여부를 정해야 한다.
  - 저장 위치: Terraform state, DB 덤프, 컨테이너 이미지를 어디에 둘지 (S3 사용 여부 포함)
